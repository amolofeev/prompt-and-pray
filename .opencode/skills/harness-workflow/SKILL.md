# Harness workflow: delivery-led маршрутизация

Исполнитель — основной агент (оркестратор). Роли исполняются как субагенты
opencode по реальным позициям IT-команды (спека: `docs/harness-agents.md`).
Оркестратор только вызывает роли через Task tool и передаёт YAML-отчёты между
ними. Этот файл — единый источник конвенций; все субагенты читают его при
старте (`Read .opencode/skills/harness-workflow/SKILL.md`).

## Конвенции (единый источник)

### Коммиты, comments, описания — [AI]
Весь AI-сгенерированный контент помечается `[AI]`.

Формат коммита:
```text
[AI] #<id> <краткое резюме задачи>


<подробное объяснение: что сделано и почему. Пункт на строку.>
```
`#<id>` обязателен сразу после `[AI]`. Коммит без задачи → сначала завести
meta-issue и сошлись на него.

Формат комментария/описания issue/PR:
```text
[AI] <краткое резюме>

<подробное содержимое>
```

### Критерий атомарности (лист графа)
Вершина — лист графа iff выполняются ВСЕ три пункта:
- один исполнимый шаг с понятным single deliverable;
- результат измерим/проверяем без других задач;
- не требует дальнейшего дробления (максимум N сабтасок / N часов).

Сформулировать критерий нельзя → вершина не готова к планированию: это задача
на анализ, её результат порождает листья (сабтаски с рёбрами от неё).

### Рёбра и ready set
- Вложенность/дерево — sub-issues: команда создания сабтаски — в skill
  `tasks-gh`.
- Рёбра зависимостей — фиксированные строки в теле задачи:
  `Depends on: #x` (блокеры: должны быть CLOSED) и `Blocks: #y`.
- Листья помечаются label `atomic`.
- Ready set: вершина READY iff все `Depends on:` блокеры CLOSED
  (проверка состояния — в skill `tasks-gh`). Открытый блокер → вершина
  BLOCKED, в работу не берётся, это ожидание.
- При раскрытии любой вершины вставлять инфраструктурные вершины
  (основа проекта, тесты, CI), которые требуют её листья; связывать как блокеры.

### Сквозные правила
- Каждый этап/задача завершается `git push`.
- Закрытие вершины может открыть новые задачи → вернуться к delivery.

### DoD-рекомендация Delivery (единый контракт)

Delivery — командная роль: она координирует поддерево, ведёт readiness и
блокеры, проверяет DoD и возвращает воспроизводимые evidence. Финальное
решение о закрытии parent принимает PO; Delivery не является его исполнителем
и не имеет close-права.

После проверки DoD Delivery возвращает существующий `route` без изменения его
полей и допустимых значений, дополняя его аддитивным блоком `dod`:

```yaml
route:
  # существующие поля route
  dod:
    target: <n>
    result: pass|fail
    recommendation: close|hold
    evidence: [ <воспроизводимые доказательства> ]
    decision_owner: PO
    state: awaiting_po_closure|hold
    target_state: OPEN
    authorization: pending|not_requested
```

Семантика блока:

- `result: pass` → `recommendation: close`, `decision_owner: PO`,
  `state: awaiting_po_closure`, `target_state: OPEN` и
  `authorization: pending`. Это рекомендация и evidence, а не close: issue
  остаётся OPEN, пока PO не примет решение.
- `result: fail` → `recommendation: hold`, `state: hold` и
  `authorization: not_requested`. При неуспешном DoD авторизация не
  запрашивается.
- `done` означает только подтверждённое фактическое закрытие target. Delivery
  не выдаёт `done` за рекомендацию, не инициирует close от своего имени и не
  может получить право выполнить close parent.
- `dod` — необязательное аддитивное расширение старого YAML-контракта, а не
  новый `route.action`; потребители, не знающие блок, могут его игнорировать.
  Фактический PO-авторизованный close и повторная проверка DoD — отдельный
  orchestration-переход вне роли Delivery.

### Переход `po_authorized_close` (вне Delivery)

`po_authorized_close` — единственный механизм harness для PO-авторизованного
закрытия parent. Его исполнитель — primary-агент/AI-команда; это не роль, не
subagent, не узел `permission.task` и не автоматическое закрытие. Переход
дополняет существующий `route` отдельным блоком `closure`, не добавляя нового
`route.action` и не меняя ни одного legacy-поля.

Вход: `route.dod` с `result: pass`, `state: awaiting_po_closure`, открытый
target и новый пользовательский запрос. До допустимого запроса target остаётся
OPEN в `awaiting_po_closure`; сам DoD-результат, молчание и отсутствие команды
авторизацию не создают.

**PO-запрос.** Обязательной slash-команды нет. Каноническая естественная форма:
`Разрешаю закрыть задачу #<n>.` Допустим эквивалентный текст только тогда,
когда он одновременно явно выражает разрешение закрыть (а не вопрос,
предположение или команду общего исполнения) и называет ровно один конкретный
target `#<n>`. Оба условия обязательны; target должен совпадать с
`route.dod.target`. PO не редактирует трекер вручную, AI не создаёт и не
выводит разрешение за PO.

Не являются авторизацией молчание, отсутствие команды, `сделай #n`,
`реши задачу #n`, голый императив `закрой #n` без явного разрешения,
рекомендация `close` у Delivery, состояние `awaiting_po_closure`, запрос без
номера, несколько target или несовпадающий target. Такой вход не запускает
переход и не меняет состояние issue.

Алгоритм primary-агента/AI-команды:

1. Через `tasks-gh` заново прочитать target и его close-комментарии. Никаких
   операций записи на этом шаге нет.
2. Проверить семантику PO-запроса и совпадение target. При невалидном запросе
   оставить `route.dod.state: awaiting_po_closure`; close не вызывать.
3. Если target уже CLOSED, найти ранее созданный close-комментарий с
   детерминированным маркером
   `<!-- harness:po_authorized_close target=#<n> -->`. При наличии маркера
   вернуть идемпотентный `done` с `dod_recheck.result: not_required`,
   `attempts: 0`, не вызывая close и не создавая комментарий. Без маркера
   вернуть `blocked`: чужое закрытие нельзя выдать за результат этого
   перехода, а новый close-комментарий запрещён.
4. Для OPEN target независимо повторно проверить актуальный DoD: перечитать
   тело/checklist parent, его `subIssues` и `Depends on:`, собрать текущее
   evidence. Это повторная проверка AI/команды, а не использование старого
   `route.dod.evidence` как неизменившегося факта.
5. При `fail` вернуть `hold`/`blocked`, `attempts: 0`; close не вызывать и
   комментарий в issue не публиковать. При `pass` сформировать close-комментарий
   по форме ниже. Непосредственно перед writer-вызовом ещё раз прочитать
   state/comments: если target уже CLOSED, применить идемпотентную ветку из
   шага 3; при ином конфликте вернуть `blocked` без записи.
6. Вызвать close через `tasks-gh` не более одного раза. При ошибке команды
   не повторять её вслепую: перечитать target и marker-комментарий. Если оба
   подтверждают успешный close, вернуть `done`; иначе `blocked` без
   `done`.
7. `done` допустим только после фактического подтверждения `target_state:
   CLOSED` и наличия marker-комментария. До этого close-результат — `hold`
   либо `blocked`.

Close-комментарий при `pass` имеет одну фиксированную форму:

```text
[AI] PO-авторизованное закрытие задачи #<n>

- Основание авторизации: <дословный PO-запрос>
- Повторная DoD-проверка: pass
- Evidence: <актуальное воспроизводимое evidence>
- Итог: задача #<n> закрыта.

<!-- harness:po_authorized_close target=#<n> -->
```

При `hold`/`blocked` до writer-вызова в close-результате сохраняется отдельный
диагностический `[AI]`-текст с причиной; он не публикуется и не содержит
утверждения о выполненном close.

Операционный контракт перехода (аддитивный sibling к `route`):

```yaml
closure:
  transition: po_authorized_close
  target: <n>
  target_state: OPEN|CLOSED
  authorization_basis:
    source: PO
    request: <дословный PO-запрос>
    target: <n>
  dod_recheck:
    result: pass|fail|not_required
    evidence: [ <актуальное воспроизводимое evidence> ]
  close:
    attempts: 0|1
    result: closed|already_closed|not_called|indeterminate
    comment:
      text: <[AI]-комментарий с маркером>
      disposition: posted|existing|not_posted
      url: <URL комментария | null>
  outcome: done|hold|blocked
```

Значения результата:

- `outcome: done` — только при `close.result: closed|already_closed`,
  подтверждённом CLOSED target и marker-комментарии; это идемпотентный итог
  фактического close;
- `outcome: hold` — авторизация допустима, но повторная DoD-проверка дала
  `fail`; writer-операция не вызывалась;
- `outcome: blocked` — конфликт, неоднозначный исход, CLOSED target без
  marker-комментария или иная невозможность безопасно подтвердить close;
  writer-операция не вызывается повторно.

`comment.disposition: not_posted` означает, что `[AI]`-текст сохранён только в
close-результате; при `hold`/`blocked` он не публикуется в issue. При успешной
операции `disposition: posted` и `url` обязательны; при идемпотентном повторе
`disposition: existing` и `url` ссылается на исходный комментарий. Старый
`route` остаётся совместимым; `closure` не выдаёт DoD-рекомендацию за close и
не предоставляет Delivery close-право.

## Оркестрация

### Паттерн узла-оркестратора дерева
Любой узел дерева — оркестратор своего поддерева (не только delivery).
Паттерн узла (шаги выбора/вызова/сбора могут повторяться):

1. (опционально) Вызови Specificator (hidden-субагент обогащения контекста):
   классификация, ограничения, артефакты. Решения маршрута он не даёт —
   выбор детей остаётся за узлом.
2. Выбери детей: из разрешённых по реестру типов узла (`permission.task`)
   реши, кого вызвать. Кого/в каком порядке/с каким контекстом — решает
   узел-родитель (отдельного «решателя»-субагента нет).
3. Вызови детей через Task tool: параллельно (несколько Task в одном
   сообщении) или последовательно.
4. Собери YAML-отчёты детей.
5. При необходимости дозови: повтори шаги выбора/вызова/сбора.
6. Агрегируй и верни родителю: единый результат (агрегация — операция
   родителя: разреши конфликты, проверь противоречия) + штатный YAML-отчёт
   роли с опциональным аддитивным `aggregate`; возврат — только прямому
   родителю.

Передавай ребёнку релевантный контекст: номер issue + предшествующие
YAML-отчёты (например требования для systems-analyst, тех.постановку для
team-lead). Полученный YAML-отчёт — единственный канал передачи результата
(не память сессии).

### Delivery — входной узел и главный маршрутизатор
Корень дерева — основной агент; вход всегда через delivery, он же главный
маршрутизатор/фолбэк.

1. Вызови субагента `delivery` с номером задачи N: Task tool,
   `subagent_type: delivery`. Он вернёт YAML `route` — куда отправить задачу.
2. Исполни маршрут: шаг выбора детей delivery — по `route.action` выбери
   ребёнка:

| action | subagent_type |
|---|---|
| requirements | `business-analyst` |
| specification | `systems-analyst` |
| planning (go) | `team-lead-go` |
| planning (python) | `team-lead-python` |
| planning (meta) | `team-lead-meta` |
| execution (go) | `developer-go` |
| execution (python) | `developer-python` |
| execution (meta) | `developer-harness` |

Для составной meta-задачи используется `planning (meta)` →
`team-lead-meta`; атомарная meta-задача остаётся в execution-маршруте
`developer-harness`.

3. Ребёнок — узел своего поддерева: сам выбирает своих детей по своему
   `permission.task` (шаг 2 паттерна) и возвращает агрегат родителю (шаг 6).
4. Возврат к delivery и петля: после каждой фазы возвращайся к `delivery` с
   обновлённым состоянием — delivery решает следующий маршрут. Цикл:

1. Delivery → маршрут → роль возвращает отчёт → delivery заново.
2. Planning создаёт сабтаски с рёбрами → delivery диктует execution по готовым.
3. После close каждой вершины снова delivery: состояние изменилось, ready set
   пересчитывается.
4. Закрытие блокера разблокирует downstream-вершины — исполнение продолжается.
5. Когда все листья родителя закрыты (parent ещё открыт) — DoD-гейт delivery:
   проверить чек-лист родителя (список sub-issues — в skill `tasks-gh`),
   собрать evidence и вернуть `dod`. При успешной проверке вернуть
   `recommendation: close`, `decision_owner: PO` и
   `state: awaiting_po_closure`, оставив issue OPEN. При неуспешной — вернуть
   `recommendation: hold`, `state: hold` и не запрашивать авторизацию.
   Delivery не закрывает parent; `done` появляется только после отдельного
   фактически подтверждённого PO-авторизованного close.

### Остановка
- Целевая вершина закрыта и её DoD подтверждён — стоп, отчёт пользователю.
- Ready set пуст, а blocked непуст — блокер: остановись и сообщи пользователю,
  какие вершины ждут и от каких зависимостей.

## Правила
- Роли не делают работу друг друга: team-lead не реализует, developer не
  планирует, аналитики не пишут код.
- delivery всегда первый; он же держит DoD-гейт родителя.
- Фолбэк без субагентов (opencode не перезапущен после добавления ролей):
  выполни фазы напрямую по конвенциям выше в том же порядке (атомарность →
  готовность → исполнение), результат тот же.
