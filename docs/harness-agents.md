# Harness: роли-субагенты opencode

Модель исполнения задач GitHub Issues через нативные субагенты opencode.
Этот документ — человекочитаемая спецификация: по нему пишется конфиг
`.opencode/agent/*.md` (#81) без доработок. Конвенции процесса (чек-лист
атомарности, формат рёбер, формат commit/close, [AI]-маркировка) живут в
skill `harness-workflow` (#82), операции с задачами (чтение/создание/рёбра/
close/ready set) — в skill `tasks-gh` (#85). Оба — единый источник правды,
на них ссылаются все роли; в промптах роли конкретные `gh`-команды не
дублируются.

## Модель: дерево рекурсивного делегирования с агрегацией наверх

Контур — дерево рекурсивного делегирования: корень дерева — primary-агент
(пользовательская сессия opencode), его единственный ребёнок — `delivery`.
Любой узел-роль — оркестратор своего поддерева: получив задачу от родителя,
сам выбирает детей из разрешённых реестром типов, вызывает их, собирает
результаты и возвращает агрегат наверх. Числовых лимитов глубины и ветвления
нет — ограничитель структурный: реестр типов узлов с разрешёнными детьми
(`permission.task`), инструменты-листья и запрет самовызова (A6.1).

Это переупаковка предыдущей delivery-led «звезды» (глубина 1, инициатива у
маршрутизатора), а не расширение: функциональность контура (маршрутизация с
прямыми адресациями и редиректами, режимы BA A/B, YAML-контракты,
планирование, исполнение, [AI]-форматы) работает как раньше; меняется только
«кто кого вызывает и как результат стекается наверх» (A7.1).

Схема:

```
Пользователь: «сделай N» / «реши задачу N»
   ▼
primary-агент (корень дерева)
   ▼
   delivery (узел-оркестратор; главный маршрутизатор/fallback; DoD-рекомендация, без close)
   ├─► business-analyst (A) ──(опц. specificator)──► агрегат ► delivery
   ├─► systems-analyst ──(опц. business-analyst (B) / specificator)──► агрегат ► delivery
   ├─► team-lead-<стек> (включая team-lead-meta) ──(опц. business-analyst (B) / specificator)──► граф ► delivery
   ├─► developer-<стек> (лист: нативные инструменты) ► результат ► delivery
   └─► developer-harness (лист: нативные инструменты) ► правка ► delivery

specificator — общий сервис предобработки (hidden): любой узел может
вызвать его первым шагом паттерна; ноль исходящих рёбер.
```

Delivery — единственный вход задач в контур и главный маршрутизатор/fallback:
новые задачи входят через него, неадресованные вопросы и редиректы
возвращаются к нему (см. раздел роли). Перед каждым выбором Delivery применяет
`harness-router` — отдельный harness-механизм состояний. Router не является
ролью или subagent и не добавляется в дерево/реестр; его нормативные правила
находятся в `harness-workflow`.

### Паттерн узла-оркестратора

Каждый узел (включая delivery) исполняет свою часть по одному и тому же
паттерну; шаги выбора/вызова/сбора могут повторяться (A1.1):

1. **(опц.) Specificator.** Вызвать общий сервис предобработки (раздел
   «Specificator»): классификация задачи + ограничения + существующие
   артефакты. Шаг необязательный, решение «вызывать или нет» — у узла.
2. **Выбор детей.** По реестру типов (`permission.task`) решить, кому
   делегировать, в каком порядке и с каким контекстом. Выбор — штатный шаг
   оркестратора-родителя; отдельного узла-«решателя» нет (A3.1).
3. **Вызов.** Вызвать детей через Task tool: параллельно (независимые) или
   последовательно (зависящие), передав каждому релевантный контекст.
4. **Сбор.** Собрать YAML-отчёты детей.
5. **(при необходимости) Дозов.** Если собранного недостаточно или отчёты
   противоречат друг другу — дозвать конкретного ребёнка с уточнением (или
   дообогатиться через Specificator).
6. **Агрегация и возврат.** Разрешить конфликты между отчётами детей,
   сформировать единый результат и вернуть агрегат родителю в штатном
   YAML-контракте роли + аддитивный `aggregate` (см. «Контракт узла»).

## Контракт узла

Каждая роль — узел дерева: принимает задачу с контекстом, работает по
паттерну узла-оркестратора и возвращает результат только прямому родителю
(A1.2–A1.3).

Вход: `task` (номер issue / промт / вопрос) + релевантный контекст — только
то, что нужно ребёнку для работы: предшествующие YAML-отчёты, артефакты,
ограничения. Не вся сессия.

Выход: штатный YAML-контракт роли (`requirements` / `specification` / `plan` /
`route` / `done` — в разделах ролей) + опциональный аддитивный блок
`aggregate`, когда узел вызывал детей:

```yaml
aggregate:
  children: [ <#n | имя ребёнка> ]
  conflicts-resolved: [ <противоречия между отчётами детей и как сняты> ]
  result: <единый результат поддерева, стекающийся родителю>
```

Правила:

- Возврат — только прямому родителю (A1.3): у ребёнка нет канала передать
  результат мимо родителя; вызов и результат всегда образуют пару
  «родитель → ребёнок → родитель».
- Агрегация — операция родителя (A1.4): разрешение конфликтов и
  формирование единого результата делает узел, вызвавший детей; отдельный
  Aggregator-узел не вводится.
- Адресование/редирект — семантика отчёта: ребёнок не перенаправляет вызов
  сам, а сообщает в отчёте, кому адресован вопрос; адресацию исполняет
  родитель (вызывает названного адресата); фолбэк — к delivery.
- `aggregate` аддитивен: он не меняет и не замещает штатный YAML-контракт
  роли (A1.2, A7.1).

## Реестр типов узлов и разрешённых детей (permission.task)

Единственный ограничитель выбора детей — реестр: матрица «тип узла → глобы
разрешённых дочерних типов» (A3.2). `permission.task` — фильтр допустимых
детей, не решатель: кого вызвать, в каком порядке и с каким контекстом решает
сам узел.

Матрица контура (источник правды):

| Узел | Разрешённые дети (permission.task) |
|---|---|
| delivery | business-analyst, systems-analyst, team-lead-*, developer-*, specificator |
| business-analyst | specificator |
| systems-analyst | business-analyst (режим B), specificator |
| team-lead-* (team-lead-go, team-lead-python, team-lead-meta) | business-analyst (режим B), specificator |
| developer-* (developer-go, developer-python, developer-harness) | — (лист: только нативные инструменты) |
| specificator | — (ноль исходящих рёбер) |

Формат строки реестра: `<тип узла> → <глобы разрешённых детей>`; `—` (пустое
множество) — лист. Глоб `team-lead-*` покрывает все позиции стека
(`team-lead-go`, `team-lead-python`, `team-lead-meta`), `developer-*` — все
developer-роли.

Синхронность (A5.1): реестр материализуется дважды — матрица в этом разделе
(источник правды) и `permission.task` в frontmatter роли (машинный фильтр
opencode). Два описания должны совпадать: правка одного влечёт правку
другого.

`harness-router` намеренно отсутствует в матрице и во всех
`permission.task`: это механизм выбора состояния, а не тип узла или
исполнительная роль. Его нельзя использовать как `route.to`, `subagent_type`
или команду выполнения.

Форма в frontmatter: поле `permission.task` — объект «паттерн → правило», а
не список. Пустое множество разрешённых детей записывается как:

```yaml
permission:
  task:
    "*": deny
```

Форма `task: []` невалидна в opencode (проверено на #91); `{ "*": deny }`
означает «ни один ребёнок не разрешён» и машино-замкнуто на 0 исходящих
рёбер.

Проверка ацикличности и запрет самовызова (A2.2): реестр проверяется
статическим обходом матрицы — транзитивное замыкание каждого узла не
содержит его самого (нет прямого и транзитивного самовызова), граф
ацикличен. Дополнительные инварианты контура: `delivery` — 0 входящих рёбер
от узлов (вызывается только корнем, primary-агентом); `specificator` и
developer-* — 0 исходящих рёбер. Проверка выполняется при верификации
контура (#99); при правке матрицы достаточен ручной обход по этим правилам.

`.opencode/skills/tasks-gh/SKILL.md` — там точные форматы, чек-листы и
команды, которые здесь не дублируются.

## 1. delivery (хаб)

Назначение: входная точка любых новых запросов «сделай N» и главный
маршрутизатор/fallback. Это командная роль: Delivery координирует поддерево,
агрегирует результаты участников, ведёт готовность (ready set) и блокеры,
проверяет DoD и возвращает evidence с рекомендацией. Финальное решение о
закрытии parent принадлежит PO; Delivery не выполняет close. Узел-оркестратор
первого уровня: входит из корня (primary-агент), делегирует ролям по паттерну
узла и возвращает агрегат корню.

Маршрутизация. Новые задачи входят через delivery. В ходе работы роли
адресуются друг другу напрямую (прямое адресование по умолчанию); получатель,
которому вопрос не адресован, редиректит отправителя — знает кого, к тому, не
знает — к delivery. Триггеры маршрута:

- результат/критерии приёмки неясны → `business-analyst` (режим A);
- вопрос роли, ответ в бизнес-реальности → `business-analyst` (режим B);
- требования есть, тех.решение неясно → `systems-analyst`;
- тех.задача стека есть, нужен план/декомпозиция → `team-lead-<стек>` (по стеку);
- составная meta-задача (label `meta`, scope контура) есть, нужен
  план/декомпозиция → `team-lead-meta`;
- атомарная и готова к исполнению → `developer-<стек>`;
- атомарная правка самого контура (агенты/скилы/спека/конфиги opencode;
  label `meta`) → `developer-harness`.
- Редирект называет адресата — маршрут туда; если адресат не назван и delivery
  тоже не может его определить — вернуть отчёт с reasoning.
- Если business-analyst вернул `needs_reply: true` — задача удерживается до
  ответа (комментарий в issue), повторный маршрут не нужен.

### DoD-гейт Delivery: evidence и рекомендация

Когда листья parent уже закрыты, Delivery проверяет актуальное состояние
родителя и его `Depends on:`/`subIssues`, собирает воспроизводимые evidence и
добавляет в существующий `route` аддитивный блок `dod`. Поля и допустимые
значения старого `route` не меняются:

```yaml
route:
  # существующие поля route
  dod:
    target: <n>
    result: pass|fail
    recommendation: close|hold
    evidence: [ <воспроизводимые доказательства> ]
    decision_owner: PO
    state: awaiting_po_closure|hold
    target_state: OPEN
    authorization: pending|not_requested
```

- Успешный DoD: `result: pass`, `recommendation: close`,
  `decision_owner: PO`, `state: awaiting_po_closure`, `target_state: OPEN` и
  `authorization: pending`. Рекомендация не является close; parent остаётся
  OPEN до решения PO.
- Неуспешный DoD: `result: fail`, `recommendation: hold`, `state: hold` и
  `authorization: not_requested`; запрос авторизации не создаётся.
- `done` означает только фактически подтверждённое закрытие target. Delivery
  не инициирует close, не выдаёт `close`-рекомендацию за `done` и не может
  получить право закрыть parent.
- `dod` — необязательное аддитивное расширение, поэтому старый YAML-контур
  и потребители, игнорирующие неизвестное поле, остаются совместимыми.
  Повторная проверка и фактический PO-авторизованный close — отдельный
  orchestration-переход, не операция Delivery.

### Переход `po_authorized_close` (вне Delivery)

`po_authorized_close` — единственный механизм harness для PO-авторизованного
закрытия parent. Его выполняет primary-агент/AI-команда; это не роль, не
subagent, не узел `permission.task` и не автоматическое закрытие. Механизм
дополняет существующий `route` отдельным блоком `closure`, не добавляя нового
`route.action` и не меняя legacy-контракт.

Вход: `route.dod` с `result: pass`, `state: awaiting_po_closure`, открытый
target и новый пользовательский запрос. До допустимого запроса target остаётся
OPEN в `awaiting_po_closure`; DoD-рекомендация, молчание и отсутствие команды
авторизацию не создают.

**PO-запрос.** Обязательной slash-команды нет. Каноническая естественная форма:
`Разрешаю закрыть задачу #<n>.` Допустим эквивалентный текст только тогда,
когда он одновременно явно выражает разрешение закрыть (а не вопрос,
предположение или команду общего исполнения) и называет ровно один конкретный
target `#<n>`. Оба условия обязательны; target должен совпадать с
`route.dod.target`. PO не редактирует трекер вручную, AI не создаёт и не
выводит разрешение за PO.

Не являются авторизацией молчание, отсутствие команды, `сделай #n`,
`реши задачу #n`, голый императив `закрой #n` без явного разрешения,
рекомендация `close` у Delivery, состояние `awaiting_po_closure`, запрос без
номера, несколько target или несовпадающий target. Такой вход не запускает
переход и не меняет состояние issue.

Последовательность:

1. Primary-агент/AI-команда через `tasks-gh` заново читает target и его
   close-комментарии; writer-операций на этом шаге нет.
2. Проверяет семантику PO-запроса и target. При невалидном входе оставляет
   `route.dod.state: awaiting_po_closure` и не вызывает close.
3. Если target уже CLOSED, ищет marker-комментарий
   `<!-- harness:po_authorized_close target=#<n> -->`. С marker возвращает
   идемпотентный `done` с `dod_recheck.result: not_required` и `attempts: 0`
   без новой операции; без marker возвращает `blocked`, не выдавая чужое
   закрытие за свой результат.
4. Для OPEN target независимо повторяет актуальную DoD-проверку по телу и
   checklist parent, актуальным `subIssues` и `Depends on:`, формирует новое
   evidence. Старое `route.dod.evidence` само по себе повторной проверкой не
   является.
5. При `fail` возвращает `hold`/`blocked`, `attempts: 0`, не вызывает close и
   не публикует комментарий. При `pass` формирует close-комментарий по форме
   ниже. Непосредственно перед writer-вызовом ещё раз читает state/comments:
   если target уже CLOSED, применяет идемпотентную ветку из шага 3; при ином
   конфликте возвращает `blocked` без записи.
6. Вызывает close через `tasks-gh` не более одного раза. При ошибке не
   повторяет команду вслепую, а перечитывает target и marker-комментарий;
   подтверждённый CLOSED + marker означает `done`, иначе `blocked`.
7. `done` допустим только после фактического подтверждения CLOSED target и
   marker-комментария; до этого результат — `hold` либо `blocked`.

Close-комментарий при `pass` имеет одну фиксированную форму:

```text
[AI] PO-авторизованное закрытие задачи #<n>

- Основание авторизации: <дословный PO-запрос>
- Повторная DoD-проверка: pass
- Evidence: <актуальное воспроизводимое evidence>
- Итог: задача #<n> закрыта.

<!-- harness:po_authorized_close target=#<n> -->
```

При `hold`/`blocked` до writer-вызова в close-результате сохраняется отдельный
диагностический `[AI]`-текст с причиной; он не публикуется и не содержит
утверждения о выполненном close.

Операционный контракт — аддитивный sibling к `route`:

```yaml
closure:
  transition: po_authorized_close
  target: <n>
  target_state: OPEN|CLOSED
  authorization_basis:
    source: PO
    request: <дословный PO-запрос>
    target: <n>
  dod_recheck:
    result: pass|fail|not_required
    evidence: [ <актуальное воспроизводимое evidence> ]
  close:
    attempts: 0|1
    result: closed|already_closed|not_called|indeterminate
    comment:
      text: <[AI]-комментарий с маркером>
      disposition: posted|existing|not_posted
      url: <URL комментария | null>
  outcome: done|hold|blocked
```

- `done` — только `close.result: closed|already_closed` при подтверждённых
  CLOSED target и marker-комментарии; это идемпотентный итог фактического
  close.
- `hold` — допустимая авторизация, но `dod_recheck.result: fail`; writer-операция
  не вызывалась.
- `blocked` — конфликт, неоднозначный исход, CLOSED без marker-комментария
  либо иная невозможность безопасно подтвердить close; writer-операция не
  повторяется.
- `comment.disposition: not_posted` означает локальный `[AI]`-текст в отчёте;
  при `hold`/`blocked` он не публикуется. При успехе disposition равен
  `posted`, при идемпотентном повторе — `existing`; в обоих случаях указан
  URL.

Переход не изменяет поля/значения `route`, не выдаёт `awaiting_po_closure` за
`done`, не создаёт роль/subagent и не даёт Delivery close-право.

### Harness-router: единый механизм выбора следующего действия

`harness-router` — harness-механизм, который из проверенных фактов выбирает
следующий шаг. Это не роль, не Task-субагент, не узел `permission.task` и не
команда выполнения. Он не создаёт и не интерпретирует авторизацию PO, не
выполняет close и не меняет трекер. Его нельзя добавить в каталог ролей или
в реестр исполнителей.

Нормативные правила и таблица состояний находятся в
`.opencode/skills/harness-workflow/SKILL.md` в разделе «Router: единый
механизм выбора следующего действия». Этот раздел — зеркало контракта для
спецификации, а не второй источник правил. Delivery применяет тот же блок к
каждому решению о следующем шаге.

#### Контракт и состояния

Router возвращает аддитивный sibling-блок рядом с legacy-`route`. Поля и
допустимые значения `route` не меняются; блок можно игнорировать старому
потребителю. `router.next.action` не является новым `route.action`. Миграция
сохраняет legacy-контракт: старые потребители читают `route`, новые — sibling
`router`; поля и значения `route` не переименовываются и не удаляются, а
отсутствие блока означает прежнее поведение:

```yaml
router:
  mechanism: harness-router
  version: 1
  state: dispatch|hold|blocked|awaiting_po_closure|done
  next:
    action: dispatch|wait|request_po_closure|stop
    to: <existing role|null>
    request: none|po_closure
    requester: PO|null
  target: <n|null>
  target_state: OPEN|CLOSED|null
  ready:
    status: ready|blocked|not_applicable
    blockers: [ <#n> ]
  authorization: not_requested|pending|present
  close: not_attempted|confirmed|indeterminate
  reason: <reproducible reason>
```

| Условия | `router.state` | `next.action` | `next.to` | Поведение |
|---|---|---|---|---|
| Открыт `Depends on:` | `blocked` | `wait` | `null` | Stop-condition: не вызывать исполнителя и не закрывать. |
| Все `Depends on:` CLOSED, вершина готова | `dispatch` | `dispatch` | одна существующая роль | Вызвать ровно одну зарегистрированную роль. |
| `needs_reply: true` или DoD `fail` | `hold` | `wait` | `null` | Только ожидание; PO-запрос и writer не запускать. |
| DoD `pass`, target OPEN, решения PO нет | `awaiting_po_closure` | `request_po_closure` | `null`, `requester: PO` | Оставить OPEN; запросить/ожидать решение PO, а явный PO-запрос передать внешнему `po_authorized_close` (S2); авторизация не создаётся. |
| PO-решение и свежий DoD подтверждены, close подтверждён | `done` | `stop` | `null` | Единственная ветка фактического `done`. |
| Конфликт, CLOSED без marker или неоднозначный close | `blocked` | `wait` | `null` | Не выдавать `done` и не повторять close. |

Ветка `awaiting_po_closure` всегда оставляет target OPEN. Если явного
PO-решения ещё нет, `request_po_closure` означает запрос/ожидание. Если вход
уже содержит явный PO-запрос, тот же семантический шаг передаётся внешнему
переходу `po_authorized_close` (S2) для проверки; только подтверждённый результат
S2 может перевести состояние в `done`. Router не трактует запрос как
авторизацию и не вызывает close.

`next.to` ненулевой только для `dispatch`; это существующая роль из реестра,
а не `router`. `hold` и `blocked` — только ожидание. `done` допустим только
после подтверждения `target_state: CLOSED` и marker-комментария
`<!-- harness:po_authorized_close target=#<n> -->`; рекомендация Delivery,
`pending` authorization или голое состояние CLOSED без marker не являются
close.

#### Readiness и границы

Delivery перечитывает зависимости через `tasks-gh` перед каждым dispatch. Открытый
blocker остаётся stop-condition и находится в `ready.blockers`; после его
перехода в CLOSED blocker удаляется из активного списка, ready set
пересчитывается, и только затем router может выбрать существующего исполнителя.
Router не создаёт и не изменяет `Depends on:`/`Blocks:`.

В реестре `permission.task`, каталоге ролей и manifest-ссылках `router`
отсутствует как исполнитель. В Delivery, developer-ролях и командах выполнения
нет вызова `router`; слово встречается только как имя harness-механизма и его
аддитивного отчёта. Механизм не даёт Delivery close-право и не превращает
PO-запрос в авторизацию.

Границы:
- НЕ исполняет задачи, НЕ пишет код, НЕ декомпозирует сам;
- НЕ создаёт и НЕ закрывает issues за других участников, включая parent;
  Delivery не имеет close-права и не может выдать рекомендацию за `done`;
- проверяет DoD и возвращает evidence/recommendation, но не инициирует и не
  подтверждает PO-авторизованный close — этот переход находится вне роли.

Разрешённые дети (permission.task): `business-analyst`, `systems-analyst`,
`team-lead-*` (включая `team-lead-meta`), `developer-*`, `specificator`.

Инструменты: `read`, `bash` (gh, git status/log); `edit: deny`.
Операции с задачами — через skill `tasks-gh`.

Вход: произвольная команда заказчика, номер issue или вопрос/редирект роли.
Выход — существующий YAML-отчёт о маршрутизации с опциональным аддитивным
блоком DoD-рекомендации:

```yaml
route:
  container: N | null (вопрос без номера issue)
  action: requirements|specification|planning|execution|done
  to: business-analyst|systems-analyst|team-lead-go|team-lead-python|team-lead-meta|developer-go|developer-python|developer-harness
  mode: A|B (только для business-analyst)
  reasoning: <почему этот маршрут>
  acceptance: <критерии приёмки, если известны>
  dod:
    target: N
    result: pass|fail
    recommendation: close|hold
    evidence: [ <воспроизводимые DoD-доказательства> ]
    decision_owner: PO
    state: awaiting_po_closure|hold
    target_state: OPEN
    authorization: pending|not_requested
```

`dod` появляется только после проверки DoD и не заменяет старые поля
`route`. Успешный результат — `close` + `PO` + `awaiting_po_closure` при
OPEN target; неуспешный — `hold` без запроса авторизации. `action: done`
допустим только при фактически подтверждённом CLOSED target и никогда не
является синонимом DoD-рекомендации.

Если состояние выбирается harness-router, Delivery может дополнительно
вернуть sibling-блок `router` из нормативного контракта:
`state: dispatch|hold|blocked|awaiting_po_closure|done`,
`next.action: dispatch|wait|request_po_closure|stop` и поля
`next.to`, `request`, `requester`, `ready`, `authorization`, `close`, `reason`.
`dispatch` выбирает только существующую роль; `hold`/`blocked` только ждут;
`awaiting_po_closure` оставляет target OPEN; `done` требует подтверждённого
close. Блок аддитивен и не является новым `route.action`.

## 2. business-analyst

Назначение: «голос заказчика в контуре» — не разовая фаза в начале, а роль,
которая возвращается в игру, когда любой участник упирается в вопрос, ответ на
который лежит в бизнес-реальности. Формализует невнятную задачу в требования
на языке заказчика: цель, ожидаемый результат, критерии приёмки, in/out,
риски, NFR — и доуточняет их по мере поступления вопросов.

Два режима:

- **A — первичная постановка.** Вход: промт в чате / тело и комментарии issue /
  комментарий к задаче без ясной приёмки. БА собирает контекст, уточняет,
  формализует требования.
- **B — реактивное доуточнение.** Вход: вопрос любой роли (systems-analyst,
  team-lead, developer) напрямую или через delivery. БА ищет ответ
  (артефакты/доки/код/эксперты) и дополняет требования.

Заказчик — человек, но не одна личность:

- Каналы: промт в чате, тело issue, комментарий к задаче.
- Слои авторства: первичный источник содержания (соседний отдел/пользователи)
  vs PO как шина и функция согласования. Уточнять можно у любого источника
  содержания, итоговое согласование БТ — всегда через PO.
- Провенанс в артефакте: `sources` / `consulted` / `approved_by`; у вопросов —
  адресат (`po|source|expert|docs`).

Цикл (приближённый, не раздутый):

1. вход (channel-aware) → 2. исследование as-is (смежные issues через gh,
   упоминания в коде/доках) → 3. понимание (резюме + as-is→to-be) →
   4. вопросы человеку (гибрид: задача есть → комментарий в задачу, нет →
   YAML-отчёт; вместо «ask nothing») → 5. аналитическая декомпозиция для себя
   (проверка полноты; НЕ тех.сабтаски и НЕ рёбра) → 6. формализация (цель,
   ожидаемый результат, критерии приёмки + in/out, риски, NFR) →
   7. вердикт (clarity, needs_reply, recommended_action).

Границы:
- аналитическая декомпозиция для проверки полноты разрешена;
- НЕ делает тех.выбор (архитектура, стек), НЕ реализует;
- НЕ создаёт и НЕ закрывает issues; работает через skills;
- НЕ строит тех.сабтаски и рёбра `Depends on:`/`Blocks:` — это team-lead;
- явный маркер `bt_approved: true|false` у требований НЕ добавляется:
  согласование БТ живёт в провенансе (`approved_by`, PO) — решение #87.

Разрешённые дети (permission.task): `specificator` (обогащение контекста
перед формализацией, по паттерну узла).

Инструменты: `read`, `bash` (gh); `edit: deny`. Операции с задачами — через
skill `tasks-gh`.
Вход: промт/issue без ясной приёмки (режим A) или вопрос роли с ответом в
бизнес-реальности (режим B).
Выход — YAML-отчёт требований:

```yaml
requirements:
  mode: A|B
  target: <issue #n | промт | вопрос роли>
  goal: <цель на языке заказчика>
  expected_result: <ожидаемый результат>
  acceptance: [ <критерии приёмки / что считать выполненным> ]
  scope:
    in: [ <в объёме> ]
    out: [ <вне объёма> ]
  risks: [ <риски> ]
  nfr: [ <нефункциональные требования> ]
  provenance:
    sources: [ <первичные источники содержания> ]
    consulted: [ <кто опрошен / что изучено> ]
    approved_by: [ <PO: итоговое согласование БТ; пусто, пока не согласовано> ]
  questions:
  - addressee: po|source|expert|docs
    asked_to: <кому задан вопрос>
    question: <вопрос>
    channel: issue-comment|yaml-report
    answered: true|false
    answer: <ответ, если получен>
  verdict:
    clarity: full|partial
    needs_reply: true|false
    recommended_action: planning|specification|await_reply
```

Режим B возвращает дополненные требования с отвеченным вопросом
(`questions[].answered: true`) — ответ уходит задавшей роли через отчёт.
Режим A с открытыми вопросами человеку: вопросы публикуются комментарием в
issue и дублируются в `questions` с `answered: false`, `needs_reply: true`,
`recommended_action: await_reply` до получения ответа.

## 4a. team-lead-meta (planner meta-стека)

Назначение: техническое планирование составных задач самого harness-контура —
агентов, скилов, спецификации и конфигурации opencode. Роль применяется к

Маршрут delivery: если meta-задача составная и не готова к исполнению как

снова пересчитывает ready set и направляет готовые meta-листья в
`developer-harness`; planner не вызывает developer напрямую. Если атомарность
или границы meta-задачи нельзя сформулировать, delivery сначала направляет
задачу на анализ, а не расширяет scope planner’а.

Матрица разрешённых детей:

| Узел | Разрешённые дети (permission.task) |
|---|---|
| team-lead-meta | business-analyst (режим B), specificator |

`developer-harness`, product developers или самого себя; граф дочерних
вызовов ацикличен.

Границы:
- планирует только meta-вершины; Go/Python-планирование остаётся у
  соответствующих team-lead;
- не исполняет код, не изменяет файлы контура, не запускает build/test/lint и
  не коммитит, не пушит и не закрывает issues;
- все операции чтения и изменения задач выполняет через skill `tasks-gh`.

Инструменты: `read`; операции с задачами выполняются через skill `tasks-gh`,
`edit: deny`. Вход: составная meta-вершина из задания delivery вместе с

```yaml
plan:
```

`plan` — существующий контракт планирования, а `aggregate` (если planner

## 6. specificator (сервис предобработки)

Назначение: один общий переиспользуемый hidden-субагент обогащения контекста
— опциональный первый шаг паттерна узла-оркестратора (A4.1–A4.2).
Классифицирует задачу (тип, сложность, домен) и собирает ограничения и
существующие артефакты — чтобы вызвавший узел точнее выбрал детей и передал
им релевантный контекст. Экземпляр один на контур, per-node экземпляров нет.

Границы:
- НЕ решает, кого вызывать: выбор детей остаётся за вызвавшим узлом; в
  выходном контракте нет полей `route` / `next_step` / `recommended_action`
  (A4.3);
- НЕ вызывает детей: ноль исходящих рёбер (`permission.task: { "*": deny }`);
- НЕ исполняет задачи и НЕ меняет код.

Разрешённые дети (permission.task): `—` (ноль исходящих рёбер;
`task: { "*": deny }`).

Инструменты: `read`, `bash` (gh); `edit: deny`. Операции с задачами — через
skill `tasks-gh`.
Вход: `task` + релевантный контекст.
Выход — YAML-отчёт обогащения:

```yaml
classification:
  task_type: <тип задачи>
  complexity: <оценка сложности>
  domain: <домен>
constraints: [ <ограничения, применимые к задаче> ]
artifacts: [ <существующие артефакты/доки/код, релевантные задаче> ]
```

Результат спецификатора возвращается вызвавшему узлу (родителю) и используется
им на шагах выбора детей и передачи контекста.

---

## Общий контракт субагента (все роли)

1. **Паттерн узла.** Любая роль — узел дерева рекурсивного делегирования и
   оркестратор своего поддерева (см. «Модель»): опционально Specificator →
   выбор детей по реестру → вызов → сбор → при необходимости дозов →
   агрегация и возврат родителю. Шаги выбора/вызова/сбора повторяемы (A1.1).
2. Прочитать скилы `harness-workflow` и `tasks-gh` перед работой — форматы и
   команды обязательны; конкретные `gh`-команды в работу не зашиваются,
   берутся из `tasks-gh`.
3. Пермишены: роли, которые не меняют код, получают `edit: deny`; дети — только
   из разрешённых реестром типов (`permission.task`), см. раздел «Реестр».
4. Комментарии/close/commit — всегда в формате [AI] (см. skill).
5. Выход — строго YAML-отчёт по контракту роли (плюс опциональный аддитивный
   `aggregate`); результат из фазы — только через отчёт (Task tool), не через
   память сессии субагента.
6. **Возврат только прямому родителю** (A1.3): результат стекается наверх
   через родителя, канала «мимо родителя» нет; агрегация — операция родителя
   (A1.4), отдельный Aggregator-узел не вводится.
7. **Запрет самовызова** (A2.2): узел не вызывает сам себя — ни напрямую, ни
   транзитивно; реестр ацикличен.
8. **Релевантный контекст:** родитель передаёт ребёнку только то, что нужно
   для работы (предшествующие отчёты, артефакты, ограничения), не всю сессию.
9. **Прямое адресование и редиректы:** роли задают вопросы друг другу напрямую
   (по умолчанию). Адресование/редирект — семантика отчёта: ребёнок сообщает в
   отчёте, кому адресован вопрос; адресацию исполняет родитель; фолбэк — к
   delivery как главному маршрутизатору. Вопрос, ответ на который лежит в
   бизнес-реальности, адресуется business-analyst (режим B).

## Расширяемость

### Добавить стек (go/python/…)

1. Два файла по шаблону: `team-lead-<s>.md` и `developer-<s>.md`.
2. В `developer-<s>` прописать стек-правила верификации (команды сборки,
   линтеры, тесты). По мере накопления стек-правила выносятся в отдельный
   skill `.opencode/skills/<s>-dev/SKILL.md`, на который агент ссылается
   (тот же паттерн, что `tasks-gh` для работы с задачами).
3. Дополнить маршрутизацию delivery: правило выбора `team-lead-<s>` /
   `developer-<s>` для задач стека `<s>` и строки реестра в матрице
   (глобы `team-lead-*` / `developer-*` уже её покрывают; правки — только
   если новому стеку нужны отдельные дети).

Для meta-стека используется отдельный planner `team-lead-meta`; атомарные
meta-листья исполняет `developer-harness`, поэтому отдельный `developer-meta`
не добавляется.

### Зарегистрировать новый тип узла

1. Создать файл роли `.opencode/agent/<имя>.md` по шаблону роли: frontmatter
   (`mode: subagent`, пермишены, `permission.task`), назначение, границы,
   вход/выход со штатным YAML-контрактом, строка «Разрешённые дети
   (permission.task)».
2. Вписать строку `<узел> → <дети>` в матрицу реестра (раздел «Реестр типов
   узлов и разрешённых детей») и, если новый узел сам делегирует, добавить
   его в `permission.task` родителя(ей); frontmatter и матрица синхронны
   (A5.1).
3. Проверить ацикличность: транзитивное замыкание нового узла не содержит
   его самого и не замыкает цикл через существующие рёбра; запрет самовызова
   сохраняется (A2.2).
4. Дополнить связанные разделы: таблицу ролей, строки «Разрешённые дети»
   у затрагиваемых ролей, при необходимости маршрутное правило delivery.

### Слот tech-lead

Когда team-lead-<s> станет несколько, над ними вводится `tech-lead`
(архитектурные и межстековые решения). Маршрутизация: delivery направляет
межстековое/архитектурное в `tech-lead`, тот уже в нужный `team-lead-<s>`.
Контракты team-lead-<s> при этом не меняются — tech-lead надстраивается
поверх.
